## 文件与分发

- 两个 Skill 的 frontmatter 有有效名称和用途，入口能找到当前阶段材料。
- 将整个 skills/ 内容复制到隔离目录后，所有本地 Markdown 引用仍可解析，不依赖本仓库的 docs/ 或脚本。
- 当前指令不依赖运行器、执行清单、适配器或自动生成的调度脚本。历史研究和旧版变更记录有明确时点。
- README 示例包含目标、工作目录或现有项目、按需新建 session 的授权；未安装 Skills 时可通过完整文件路径读取。

## 情境走查

用下列情境检查提示词给出的下一步是否明确；桌面推演应标记为模拟，不调用真实外部会话即可完成。

| 情境 | 可观察的预期结果 |
| --- | --- |
| 新项目需求已确认，任务很小 | 采用已有确认，按需合并材料和任务，连续推进，不逐阶段索要“继续”。 |
| 现有项目有未提交改动 | 核对并保留用户改动，保存脏基线所需的暂存、未暂存变化及未跟踪文件原始内容（含二进制）；保存不完整时禁用自动回退，接力不重设基线。 |
| 当前上下文过重，宿主可创建和查询会话 | 保存外部交接，登记等待接手并停止写入，再创建和启动后继；后继核对并确认接手后开始写入，原会话保持只读。 |
| 宿主只有子代理，或完全没有新会话工具 | 如实区分审核、委派和新聊天能力；能继续则继续，确需人工接力时先保存不可变快照、登记等待后继的交接引用并停止写入，再给用户可直接发送的提示词。 |
| 创建超时但后继可能已启动 | 查询原调用、检查接手记录，避免重复创建或并发修改。 |
| 任务已审核，随后修复或更换实现会话 | 沿用审核与预算；主 Agent 验证新版本，不另派 reviewer。 |
| 两轮修复仍失败，或三个实现会话用尽 | 先保存失败证据；只在已核实的隔离工作树内考虑回退；预算不重置，继续独立任务。 |
| 缺少独立审核能力或验证环境 | 记录具体待审核/待验项，区分实际缺陷，不宣称全部完成。 |
| 交付后的补验发现回归 | 从当前已接受成果建立关联修复，不回退旧任务并撤销后续交付。 |
| 宿主退出或原会话失联后继续 | 先核对文件、Git、活跃会话、已派审核和记录，再接手；不能证明旧写入者停止时先处理所有权。 |

## 真实宿主验证

使用隔离的小项目和现有登录，在符合宿主权限的前提下验证以下一条完整路径：确认需求 → 规划审核 → 实现 → 保存交接 → 真正启动后继 → 接手并继续 → 任务唯一一轮独立审核 → 修复验证 → 本地交付。按实际需要选择换会话的位置，不为测试强制拆出多余产品任务。

保存宿主名称与版本、实际调用工具、会话 ID、交接路径、接手确认、最终文件或提交和检查结果。验证后继在原会话结束后是否继续存活；如依赖原会话保持活跃，明确这一限制。审核、预算和原工作区保护的结论必须有对应证据。

完成实测后更新本页的验证记录与待验项，并在 progress.md 追加摘要；只清除有实际证据支持的待验项。
