# Autoship：真实工作流与 Wiki 证据

历史说明（2026-11-12）：项目已改为纯提示词，本文保留原始流程依据，旧运行器建议由 [产品方案](../PROPOSAL.md) 替代。

调研日期：2026-11-11。范围：通过 Wiki MCP 阅读相关知识库条目，回到一手来源校准，再对照 FloatDo 从零开发与剪贴板历史增量的真实聊天和项目记录。本文件是设计依据，不新增产品要求，不代表任何自动化适配已验证。

后续要求更新：用户在本次 Autoship 讨论中明确每个 task 只做一轮子代理 review，不重复审核。本文引用的 FloatDo 历史规则仍保留原貌；其中“必要时复审”的例外不适用于 Autoship，当前规则见 [产品方案](../PROPOSAL.md)。

## 1. 核心发现

用户已有可用的方法，最重复的工作是等待结果、指定下一阶段、复制执行模板、修改任务编号、开启新聊天。Autoship 应优先自动化这些交接动作；产品取舍与审美方向仍由用户决定，技术判断和实现交给宿主 Agent。这个结论来自两次独立开发过程，而非从某个框架倒推需求。[F1][F2][F3][F6][F7]

真实流程也不是“所有项打勾才能继续”的直线：环境缺项曾被明确延期，已发现的缺陷则需要修复；局部交付、整体验收、正式发布是不同事实。任务状态必须保留这种区别，不能因为进程退出、review 完成或已经发布就判定全部通过。[F4][F5][F9][F10]

## 4. FloatDo 从零开发：实际交接链

| 阶段 | 用户实际手动动作与证据 | 应保留的能力 |
| --- | --- | --- |
| 澄清 | 要求 grill-me，逐轮回答；随后让 Agent 调研 WinIsland、Atoll，并强调由自己作产品取舍。[F1] | 主动追问、事实自行调查、产品决定由用户确认。 |
| 产品与技术文档 | 在同一澄清聊天中分别发送“写 prd.md”“完成 TECH_STACK.md”；另开聊天要求设计文档。[F1][F2] | 需求确认后自动组织必要材料；文件数量不成为成功指标。 |
| 项目约定 | 要求精简 AGENTS.md，并加入独立 review 和简短 progress.txt。[F2] | 继承项目已有约定，不重复灌入通用长提示词。 |
| 计划与拆任务 | 先要求实施计划，再要求拆 tasks.md，最后纠正为按执行顺序逐 task 组完成。[F3] | 有前置关系的顺序可交付任务组，允许一组包含多个原子任务。 |
| 逐组实施 | TASK-01～06 分别使用新聊天；重复同一模板，只改任务编号。[F4] | 自动构造当前任务的启动信息与引用，自动接到下一任务。 |
| 验证与审核 | 模板要求实施、验证、同步文档、commit、报告未验项；AGENTS 要求独立 review 后由主 Agent 修复。[F4][F8] | 这些要求随每次交接保留，无需人工重复发送。 |
| 补验与再接力 | 用户明确延期实机验证，随后另行要求补 TASK-04/05 验收；又要求完成后创建新聊天并发送 TASK-07–08 模板。[F5] | 环境延期不抹掉待验项；新会话交接不是仅靠对话记忆。 |

原执行模板的主要含义是：先读任务与依据、检查前置，完成本任务；常规可逆选择自行判断；更新状态和进度；只提交本任务改动；阻塞时完成独立部分，未验项不得标完成；报告验证与 commit。它已经接近执行 Skill 的输入契约，不需要重新发明一套开发方法。[F4]

历史记录表明，用户需要在一次工作结束后自动开启或恢复下一会话；不能仅凭需求记录认定自动创建已经成功。[F5]

## 5. 已有项目增加剪贴板历史：不同入口，共用执行方法

一次已有项目的功能开发先澄清增量范围和设计约束，再同步文档、审核计划，并通过短模板接续执行。[F6]

CH01–CH02 与 CH03–CH04 在不同聊天中使用相同短模板：读 AGENTS、需求、源码研究与计划审核；遵守已确认范围；完成实现、必要验证与独立 review；修复有效问题；满足完成条件才勾选；同步文档与 progress；提交代码。[F7]

这条路径支持如下研究判断：

- **已有工程应先建立增量边界。** 开发计划显式指出不重排首发 Task 01–28，复用当前工程，阻断本功能的前置需先补验/修复，无关历史缺项保留原状。[F9]
- **规划审核有实际价值。** 计划审核记录指出 5 类缺口，并调整热键迁移、焦点捕获、原生线程/对象寿命、富文本合并前置与排序提交点。它同时明确这些是计划修正，不是代码验收通过。[F10]
- **参考成熟项目不是无条件复刻。** 研究和审核保留 Ditto 的产品语义，检查其实现局限，不引入未采纳功能；技术适配不得暗中变成产品扩张。[F10]
- **状态只设一个权威来源。** 增量计划要求任务状态集中在功能开发计划，根 tasks.md 仅索引与映射，避免两套独立勾选。[F9]
- **同一物理环境不能被多个 Agent 争用。** 计划明确原生剪贴板/焦点测试串行执行；独立 review 只读代码，真实桌面验证由主 Agent 执行。[F9][F11]
- **开工时必须处理已有改动。** CH01–CH02 的起点含其他未提交工作，用户明确选择先单独提交既有改动再提交本次实现。自动化不能把“保持工作区干净”理解为覆盖、丢弃或混入原改动。[F7]
- **主观设计反馈可以在实施中出现。** CH08 过程中用户再次提供参考图并要求打磨，这种新方向必须作为显式变更同步，不应由流水线自动杜撰。[F12]

## 6. 哪些固化为 Skill，哪些交给脚本

以下是基于证据的职责建议，不是新增强制文件格式或运行时选型。

| 工作 | 适合放在哪里 | 理由与来源 |
| --- | --- | --- |
| 追问目标、比较候选、检查代码事实、识别范围变更 | 澄清/调研 Skill，由 Agent 判断 | 问题随用户答案变化，不能用固定问卷穷举。[F1][F6][R1] |
| 选择必要文档、形成方案、划任务、检查文档一致性 | 规划 Skill，由 Agent 判断 | 新项目与 feature 输入不同，但都需要形成可执行增量。[F3][F6][F9][F10] |
| 实现、选择相关测试、解释异常、评估 review 发现 | 执行/审核 Skill，使用宿主工具 | 需要工程判断；用户已要求让高能力模型发挥。[F2][F4][F7] |
| 启动新会话、给定 cwd/任务、保存会话 ID、接收退出状态 | 小脚本与宿主适配 | 是重复、可观察的进程操作；用户要消除的主要手工动作正是这里。[F4][F5][F7] |
| 次数预算、检查点、失败记录、原子状态保存、重启核对 | 小脚本 | 必须跨会话保持准确；仅在提示词里要求记住不能形成确定性计数。此项是工程判断，验证依据是跨会话接力的实际需求及磁盘交接经验。[F5][R5] |
| 判定是否允许推进 | 脚本核对结构结果，Agent 提供判断与证据 | 不能只解析“完成”字样；需区分通过、环境待验、真实失败、产品待决。脚本验证结构与已知约束，不能独自判定任意产品是否正确。[F5][F9][F11] |
| 产品范围、重要交互、审美目标、无法自动取舍的新决策 | 用户 | 用户反复强调由自己决定取舍，后续图稿反馈也表明审美不是代码测试能完全替代的。[F1][F6][F12] |
| 环境暂不可用 | 按已确认规则记录并继续独立工作；必要时用户参与 | 历史上用户明确允许延期，但不得据此把所有环境缺项永久放行。[F5][F9] |

“只有短 Skill”与“只有循环脚本”都不覆盖完整需求：前者无法保证宿主结束后被重新启动，后者不知道下一步怎样做才符合产品目标。需要保留的最小边界是方法、执行状态、用户决定，而不是多 Agent 角色数量。[F4][F5][R4][R5]

## 7. 应避免的过重或不可靠做法

1. **让长提示词承担可靠状态管理。** 重试计数、检查点和实际任务 ID 是程序数据；更长的“务必遵守”不能替代它们。文件可被 Agent 修改也意味着本地状态不是安全隔离边界。这是本研究的工程判断。[F5][R5]
2. **默认建通用图编排平台、数据库、常驻调度服务。** FloatDo 已有单仓库顺序任务组和文件交接证据，尚无需要这类新增基础设施的行为证据。首先检验一条本地顺序流程能否满足已确认轻量约束。[F3][F7]
3. **把定时唤醒误当任务完成后的交接。** 用户的触发点是本阶段完成与任务前置满足；等待固定时间既不能证明完成，也不能消除空等。此项是从原话推得的产品要求。[F5]
4. **无限重试或默认每次修复重新全量 review。** 用户明确要求通常每会话一次独立审核，修有效问题；剪贴板记录也反复采用有针对性的复验。例外需由变化是否使前次审核失效判断。[F2][F8][F11]
5. **维护需求、tasks、JSON 清单、progress 四套独立真相。** 需求描述、可读进度和运行状态职责应清楚；功能计划已示范只在一处维护勾选状态。[F9]
6. **每个小改动重写 PRD、技术栈或整套项目约定。** feature 路径需要引用已有约束并同步受影响部分；同一套文档流程强套所有任务只会增加差异与审核负担。[F6][F9]
7. **用静态 review、模拟环境或截图替代真实验收。** FloatDo 明确区分原生系统行为、开发截图、Office 接收端以及真实硬件矩阵；未测不应自动变通过。[F9][F10][F11]
8. **把上游方法论全盘装入核心。** 可学习 Matt 的组合方式、Superpowers 的衔接、Ralph 的外循环和 Anthropic 的交接；本项目不必因此引入整套框架、强制每项 TDD、固定海量检查项或全局自动触发规则。此项是结合本次用户流程与一手机制的取舍建议。[R1][R2][R4][R5]

## 8. 用真实行为评估是否值得做

第一批回放应覆盖两种入口，而不是只跑一个“生成 TODO App”的演示：从已确认的新项目需求走到顺序任务；从已有工程新增一个有回归要求的功能。比较的主要量是用户为流程推进而发送的消息次数、是否误标完成、真实验收是否满足、恢复后是否重复提交或遗漏任务。[F1–F12]

还应特意重现四类 FloatDo 已出现的情况：已有未提交改动；可延期的硬件/桌面条件；review 后修有效问题；中途用户补充产品/视觉要求。它们比预先创建很多角色更能检验 Autoship 是否保留了手工流程的质量。[F5][F7][F11][F12]
